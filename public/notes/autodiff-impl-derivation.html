0. 坐标系：从算法到脚手架

Lec4 证明了反向模式 AD 的算法（伴随值反向递推 + 扩展计算图）。这一课是实现课——TQ 直接走读 needle 的代码库，讲清楚支撑那套算法的数据结构。needle = Necessary Elements of Deep Learning（也双关"缝衣针"，把神经网络缝起来）。

为什么值得单独一课：算法看懂 ≠ 会实现。TQ 指出整个 needle 才 ~1000 行（autograd ~400 + ops ~300），却含深度学习框架的全部基本元素。hw1 就是补全其中的空。这一课的目的：让你知道每个类的职责、数据往哪流，再去填 compute/gradient 才不盲目。

1. 三个核心类：Value / Op / Tensor

类职责关键点
Value计算图里的一个节点（一个中间值）不只存数据，还存"怎么算出来的"
Op一种运算（加、乘、exp…）每个 op 定义 compute + gradient
TensorValue 的子类，用户直接用的张量几乎不加字段，全继承自 Value

1.1 Value 的字段：为什么张量不只是"一坨数据"

朴素想法：张量 = 一个多维数组。但 needle 的 Value 有四组字段，远超"存数据"：

class Value:
    cached_data   # NDArray：算出来的数据（≈ numpy 数组）
    op            # Op：这个值由哪个运算得到（叶子节点为 None）
    inputs        # List[Value]：喂给该运算的输入节点
    requires_grad # bool：是否要对它求梯度
关键洞察：op + inputs 记录了"这个值怎么来的"——把 Lec4 的计算图编码进了数据结构本身。$v_4 = v_2 \cdot v_3$ 就表示成：v4.op = 乘法、v4.inputs = [v2, v3]。顺着 inputs 往回走就能遍历整张计算图（DAG）——这正是反向传播要的。叶子节点（输入）op=None、inputs=[]，数据直接在 cached_data。

1.2 Op 的两个方法：compute 与 gradient

每个 Op 子类（如 EWiseAdd、AddScalar、EWiseMul）实现两个方法：

方法输入类型职责
compute(*args)NDArray（裸数组）前向：给底层数组，算出输出数组
gradient(out_grad, node)Tensor（计算图节点）反向：给输出伴随，算各输入的部分伴随（VJP）
最容易忽略、也最关键的一点：compute 收/发 NDArray（只算数值），gradient 收/发 Tensor（构建新计算图）。为什么 gradient 不直接算数值？因为梯度本身也要能再求梯度（gradient of gradient，Lec4 讲的二阶导免费）。gradient 里做的每个运算都会再建计算图节点，于是伴随值也是一张可微的图。这是 hw1 里 gradient 必须返回 Tensor（而非 numpy）的根本原因。

2. 计算图怎么建起来：x1 + x2 背后发生了什么

写 y = x1 + x2，TQ 一步步追踪调用链：

  1. __add__ 运算符重载 → 检测到两个 Tensor → 调 EWiseAdd()(x1, x2)
  2. TensorOp.__call__ → Tensor.make_from_op(op, inputs)
  3. make_from_op 用 Tensor.__new__ 造对象（绕开面向用户的 __init__），再 _init 填字段：op、inputs、requires_grad…
  4. 但 _init 不做加法计算——只填元数据。真正的加法在 realize_cached_data() 里
拆两半的意义：建图（填 op/inputs）和算数（realize_cached_data 调 op.compute）是分开的两步。这就为下一节的 eager/lazy 两种模式留了口子——建图后立刻算 = eager，先只建图、要用时才算 = lazy。

3. eager vs lazy：什么时候真正做计算

建图和求值分离后，有两种策略：

🎬 交互：eager 与 lazy 两种求值模式对比
选模式，点"下一步"逐步构建 v₂=exp(v₁), v₃=v₂+1, v₄=v₂·v₃
蓝色 = 节点已建（op/inputs 就位，cached_data 仍空）； 绿色 = cached_data 已算出。
Eager：每建一个节点立刻算（建完即绿）。Lazy：先把图建完（全蓝），最后一次性触发计算（末尾统一变绿）——需要数据时（.numpy()/.shape）才 realize。
Eager（needle/PyTorch 默认）Lazy
何时算建图同时立刻算先建图，用到时才算
优点建图开销被计算掩盖；调试直观能看到整张图，做算子融合等优化
代价看不到全局图，难优化建图与计算分离
讲课实例：needle.autograd.LAZY_MODE=True 后，y=x1+x2 的 cached_data 是 None，直到 y.numpy() 才触发 realize_cached_data。TQ 提到 PyTorch 的 TPU 后端（XLA）就用 lazy tensor 攒一批再算。needle 默认 eager，但两种都支持。

4. 内存陷阱：为什么循环累加会爆内存

TQ 举了个"跑几轮就 OOM"的真实场景：

sum_loss = ndl.Tensor(0)
for i in range(100):
    sum_loss = sum_loss + x * x   # 看似只留一个变量
陷阱：sum_loss 看似单个变量，但它是计算图节点——每轮的 + 都把上一轮整条图挂进 inputs。100 轮后 sum_loss 拖着一条 100 节点的长链，全在内存里。这正是 PyTorch 训练循环 OOM 的常见原因。
解法：detach。y.detach() 返回一个新 Tensor，只含 cached_data、inputs=[]、op=None——斩断计算图，只留数值。当你确定不再需要对某个量求梯度时（如累加纯标量 loss 做显示），detach 掉，图就不会无限增长。PyTorch 里对应 .detach() / torch.no_grad()。这是"框架能追踪计算图"的副作用——好处是能自动求导，代价是不主动切断就会一直攒图。

5. gradient 为什么返回 Tensor（呼应 Lec4 的二阶导）

回到 §1.2 埋的伏笔。以 $v_4 = v_2 \cdot v_3$ 为例，其 gradient 要算两个部分伴随（Lec4 的规则）：

$$ \overline{v_{2\to4}} = \bar v_4 \cdot \frac{\partial v_4}{\partial v_2} = \bar v_4 \cdot v_3, \qquad \overline{v_{3\to4}} = \bar v_4 \cdot v_2 $$

needle 里 EWiseMul.gradient(out_grad, node) 就返回 (out_grad * v3, out_grad * v2)——注意这里的 * 又是 needle 运算，会再建计算图节点。

为什么这样设计（Lec4 的实现落地）：因为 gradient 用的是 Tensor、返回的伴随值也是计算图，所以对 sum_loss 的梯度 $\bar v$ 还能再求梯度——二阶导免费。对比 compute 只吐 NDArray（纯数值、不建图），职责清晰：compute 管"怎么算数"，gradient 管"怎么建可微的梯度图"。
框架还提供 op.gradient_as_tuple(...)，无论 gradient 返回单值还是多值，统一成 tuple，方便反向遍历时处理。

8. 关键概念汇总

概念作用要点
Value 节点计算图的节点op+inputs 编码"怎么来的"，非仅存数据
Op.compute前向数值计算收发 NDArray，用 array_api
Op.gradient反向建梯度图收发 Tensor，为二阶导
make_from_op内部构造图节点建图与算数分离
eager/lazy求值时机默认 eager；lazy 便于全局优化
detach斩断计算图防循环累加 OOM
array_api后端数组接口现 numpy，将来换 GPU NDArray
一句话总览（讲课主线）：needle=Value+Op+Tensor 三类 → Value 用 op+inputs 把计算图编码进数据结构 → x1+x2 经运算符重载 → make_from_op 建图、realize_cached_data 算数（分离）→ eager 立刻算 / lazy 攒着算 → detach 斩图防 OOM → gradient 返回 Tensor 而非数值，因为梯度也要可微（二阶导）→ 这套 ~1000 行骨架就是 hw1 要填的空。

附录 A：__new__ vs __init__ 为什么要用前者建图（默认知识）

讲课提到 make_from_op 用 Tensor.__new__ 而非直接构造。补充原理：

最好理解的角度：Python 建对象两步——__new__ 分配实例、__init__ 初始化。needle 的 __init__ 已被面向用户占用（接收 numpy 数组/列表造张量）。但内部建图节点时，数据来自"op 作用于 inputs"，不是用户传的数组。若复用 __init__ 会语义冲突。于是用 __new__ 拿到空实例，再调内部 _init 填 op/inputs 等字段——两条构造路径互不干扰：用户路径走 __init__，框架内部路径走 __new__ + _init。

附录 B：requires_grad 的传播规则（默认知识）

最好理解的角度：_init 里算一个节点的 requires_grad 规则是——只要任一输入需要梯度，本节点就需要（逻辑或）。直觉：梯度要能从需要求导的叶子（如参数）一路传到输出，中途每个节点都得在"可微链"上。反之，若所有输入都不需要梯度（如纯常量运算），本节点也不必留梯度信息，省内存。这跟 §4 的 detach 是一体两面：detach 手动把 requires_grad 断掉，这里是自动按输入推导。
